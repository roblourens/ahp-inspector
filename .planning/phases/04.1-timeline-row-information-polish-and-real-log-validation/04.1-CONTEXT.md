**Gathered:** 2026-05-08
**Status:** Ready for UI-SPEC, research, and planning
**Source:** User feedback during Phase 5 planning handoff

<domain>

## Phase Boundary

This inserted phase must improve the core timeline row experience before theme/polish work starts. It should not redesign the whole visual system or start Phase 5 theme work.

<decisions>

## Locked User Decisions

### Timeline column order and status presentation

- Move the ID column to be the first timeline column.
- Remove the standalone status column because its meaning is unclear to the user.
- Error rows must still be clearly annotated as errors through a row badge, row tone, method/type label, icon, or other understandable inline annotation.

### Request/response relationship

- When a request row is selected, highlight the corresponding response row.
- The highlight should help users follow the pair while browsing the timeline and should remain understandable when filtering/searching/navigating.

### Session and turn data

- The session and turn columns are currently empty in practice and must be fixed if those values are present in the source JSONL.
- If a row has no session/turn, that should reflect source data absence rather than extraction failure.

### Row summary replacement for payload preview

- Replace the generic row payload preview with event-specific parsed summary text.
- Summaries should extract the most useful fields for each event shape rather than showing arbitrary JSON.
- Examples the user specifically called out:
  - `resourceList` should show the requested URI.
  - `delta` should show content.
  - tool rows should show the tool name and useful args when possible.
  - action/notification/protocol rows should show the relevant event-specific fields that help understand the event at a glance.
- The detail sidebar must still show the full event details when a row is selected.

### Detail Pretty JSON default

- The Pretty JSON view should always be expanded by default.
- Users may still collapse/expand while inspecting details, but the initial state should favor immediate readability.

### Action marker clarity

- The small marker next to action rows is confusing because it reports `action row family unknown`.
- Either remove it or replace it with a useful, understandable taxonomy. Do not expose unknown/internal taxonomy labels to users.

### Real-log fixture

- The user provided a real JSONL file at `~/ahp-2026-05-08T03-02-25-575Z-ssh-macbook-air.jsonl`.
- The phase should use it for testing and validation, but only after privacy review/scrubbing.
- If copied into the repo, the committed fixture must not contain secrets, private prompts/output, tokens, personal absolute paths, hostnames/usernames, or other sensitive data.

</decisions>

<specifics>

## Specific Ideas

- Rename the row preview concept from "payload" to something like "summary" or "details" if the UI labels it.
- Prefer concise event-specific patterns:
  - `resourceList uri=<uri>`
  - `delta "<content snippet>"`
  - `tool <name> {arg summary}`
  - `error <code/message snippet>`
  - `session <operation> <sessionId/turnId if useful>`
- Keep row cells single-line and truncating; full data remains in detail view.
- Use visual pairing that is noticeable but not loud: selected request row remains primary, matched response row gets a secondary highlight/rail.
- If the matching response is filtered out, the UI should not imply no response exists; plan should decide whether to show a subtle hidden-match indicator or rely on detail correlation metadata.

</specifics>
