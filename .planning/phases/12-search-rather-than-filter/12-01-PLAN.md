<objective>
Separate search from filtering in UI state.

Purpose: Search should locate matches while preserving timeline context; filters should remain the explicit row-narrowing mechanism.
Output: Store and selector contracts that downstream UI can consume without treating search as a filter.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> search endpoint | Search query crosses from UI state into `/api/log/search`. |
| server result -> UI state | Match indexes returned by the server drive UI navigation/highlighting. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01-01 | D | useSearch/store.ts | mitigate | Preserve debouncing, abort handling, server-side query cap, and result cap; do not add client-side full-payload scans. |
| T-12-01-02 | T | selectors.ts | mitigate | Treat server match indexes as row indexes only after intersecting with existing rows/visible rows; ignore out-of-range indexes in helper logic/tests. |
| T-12-01-03 | I | store persistence | accept | Search query persistence already exists for local-only current-log preferences; no new outbound data path is introduced. |
</threat_model>
