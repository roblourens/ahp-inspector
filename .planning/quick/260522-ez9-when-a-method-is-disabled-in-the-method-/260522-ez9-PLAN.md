# Quick Task 260522-ez9

## Description

When a method is disabled in the Method facet, hide both requests for that method and their matching responses. `ping` is hidden by default, so `ping` responses should also be hidden by default.

## Diagnosis

The previous quick task changed the Method facet into a checked visibility list backed by method exclusions: `APP_DEFAULT_FILTERS.method` starts as `["ping"]`, and `FilterBar` renders discovered methods checked except hidden methods. The remaining gap is in row filtering. `packages/ui/src/state/filters.ts` only evaluates `row.method`, so request rows hide correctly but matching response rows usually keep `method: null` and remain visible.

Rows already carry correlation metadata via `EventRow.pairIdx` from `packages/core/src/row-projection.ts`, populated by the server from `Correlator.pairIdx`. The UI selector can therefore hide a response when its paired request has a hidden method without changing parser, server, or core correlation behavior.

## Tasks

1. Add pair-aware method exclusion tests first.
   - Files to inspect/edit: `packages/ui/src/state/selectors.test.ts`, `packages/ui/src/state/filters.ts`, `packages/ui/src/state/selectors.ts`, `packages/core/src/row-projection.ts`.
   - Add focused selector coverage showing that `APP_DEFAULT_FILTERS` hides both a `ping` request row and its paired response row when the response has `method: null` and `pairIdx` points back to the request.
   - Add a second selector case showing that when another method such as `tools/call` is added to `filters.method`, both the `tools/call` request and its paired response are hidden while unrelated response rows remain visible.
   - Keep existing behavior covered: null-method rows with no hidden-method pair should still pass method exclusions.

2. Make method facet filtering correlation-aware in the UI selector layer.
   - Files to inspect/edit: `packages/ui/src/state/filters.ts`, `packages/ui/src/state/selectors.ts`, `packages/core/src/row-projection.ts`.
   - Preserve `applyFacets(row, filters)` as the row-local predicate for non-correlated checks, or extend it only if the call sites stay clear and type-safe.
   - In `useFilteredRows()` and `useVisibleSearchMatches()`, evaluate method exclusions using the row's own method when present, otherwise look up `row.pairIdx` in the current `rows` array and use the paired row's method when available.
   - Do not infer methods from payload text, summaries, ids, or row order. Use only `EventRow.pairIdx` and the paired `EventRow.method` so JSON-RPC request/response correlation remains the source of truth.
   - Keep all other facets as their existing row-local inclusion filters; this change is specifically about Method facet exclusions propagating across matched request/response pairs.

3. Verify the quick task with focused tests and the UI type gate.
   - Files to inspect/edit: `packages/ui/src/state/selectors.test.ts`, `packages/ui/src/state/filters.ts`, `packages/ui/src/state/selectors.ts`.
   - Run `pnpm -F @ahp-inspector/ui test -- selectors.test.ts`.
   - Run `pnpm -F @ahp-inspector/ui typecheck`.
   - If the implementation touches Method facet UI behavior, also run `pnpm -F @ahp-inspector/ui test -- FilterBar.test.tsx selectors.test.ts`.

## Done When

- With default filters, `ping` requests and their paired responses are both absent from `useFilteredRows()` output.
- When a user unchecks another method in the Method facet, requests for that method and their paired responses are both absent from the timeline.
- Responses with no pair, or whose pair has no hidden method, remain visible unless another active facet excludes them.
- Search navigation visibility uses the same pair-aware method exclusion logic as the timeline.
- Focused UI tests and `@ahp-inspector/ui` typecheck pass.
